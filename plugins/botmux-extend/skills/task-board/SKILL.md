# 任务看板（muxboard）

muxboard 是封装飞书多维表格的命令行工具，作为多个 bot 协作的任务看板。每个任务是一条记录，记着标题、负责人、状态、优先级、依赖、父子关系和产出。

只通过 `muxboard` 访问看板。不要直接用 lark-cli 读写这张表。所有命令输出 JSON。

核心规则：

- 一个 bot 同一时间只处理一个任务。不要同时接、同时做多个任务。
- 先做前置任务，再做依赖它的任务。总设计、接口约定没完成，子模块不开工。
- 计划存在看板上（依赖、优先级），不靠记忆。每次决策前从看板重新读取。

## 收到任务

1. 执行 `muxboard show <任务ID>` 读取详情（描述、准出标准、父任务、依赖）。
2. 执行 `muxboard start <任务ID>`，状态改为进行中。
3. 判断要不要拆：任务包含多个能独立完成的交付物，或一个人做明显耗时过长时，按下面「拆分与调度」处理，不要自己从头做到尾。
4. 不拆就按描述开展工作。描述里的参考文档链接需要时自己打开；依赖任务的产出用 `muxboard show <依赖ID>` 查看。
5. 完成时对照准出标准，见下面「完成」。

## 被唤醒但不清楚上下文

在工作群里被消息唤醒时，你没有之前的对话记录。

1. 从群里的说明消息或收到的消息里找到任务 ID（rec 开头）。
2. 执行 `muxboard show <任务ID>` 看自己的任务，执行 `muxboard children <任务ID>` 看所有子任务进展。
3. 你是派发方（任务有子任务）时，按「调度一轮」继续调度，并做「巡检」。不要凭记忆假设进展。

## 拆分与调度

流程：规划 → 一次建好全部子任务（写依赖和优先级）→ 调度。派发方在协调期间不领子任务，只负责规划、调度、解阻塞和收尾。

### 1. 规划

对照准出标准，列出要做的所有事，不只是"写代码"。常见的有：总体设计或接口约定、各模块实现、测试用例、集成、验收、文档。

- 每个子任务只有一个明确产出（一个模块、一组测试、一份文档），准出标准可以检验。
- 定义类任务（总体设计、接口约定、数据结构）是使用它的子任务的前置依赖。子模块要等它完成，按它的产出开工。
- 依赖要真实：后一个任务确实要用到前一个的产出才写依赖；确实要用到就必须写，不要为了多开工而省略。
- 不要让两个子任务改同一个文件。需要合成一个产物时，按模块分开开发，再用一个集成子任务合并（依赖全部模块）。
- 设优先级：在关键路径上、被别人依赖的任务优先级高。

### 2. 控制粒度

- 合适的子任务：一个 bot 不需要再协调别人就能完成。
- 子任务本身又包含多个独立交付物时，照样作为一个子任务，并在描述里写明"需要继续拆分"。负责的 bot 收到后按本节继续拆。
- 不要过度拆：几分钟就能做完的事不必单独建任务，拆分和集成本身有成本。

### 3. 写清子任务

每个子任务的 `--desc` 写明：

- 背景：根任务要做什么，一句话。
- 要做什么、不做什么（边界）。
- 依赖谁、要用到依赖的哪部分产出；已有的约定原文写进来。
- 产出的位置（文件路径、链接）。
- 谁会用它的产出。

`--criteria` 写成可检验的条目。

### 4. 一次建好全部子任务

1. 你的任务是子任务（不是根任务）时，先执行 `muxboard split <自己的任务ID>`。CLI 会为它新建工作群，把上级群里的人和 bot 拉进来。根任务不需要这一步，它的工作群就是根群。
2. 按依赖顺序执行 `muxboard add <父任务ID> --title ... --desc ... --criteria ... --priority <高|中|低> --deps <依赖ID,...>`，把规划里的全部子任务一次建好，状态为待分配。被依赖的任务先建，拿到 ID 后填进后续任务的 `--deps`。依赖只能是同一父任务下的子任务。
3. 建完不要逐个派发，进入「调度一轮」。

### 5. 调度一轮

1. 执行 `muxboard children <父任务ID> --ready`，得到可派发的任务（待分配、没有负责人、依赖都已完成），已按优先级排好序。
2. 按顺序取任务，选一个工作群里的空闲 bot，执行 `muxboard assign <子任务ID> --bot <app_id>`。每个空闲 bot 最多派 1 个任务。
3. 派到没有空闲 bot 或没有可派发任务为止。其余任务保持待分配，就是在排队。
4. `assign` 的拒绝：
   - `bot_busy`：这个 bot 手上已有任务，换下一个 bot。所有 bot 都忙时停止，在工作群里说明"等待 bot 空闲"。
   - `deps_unfinished`：依赖还没完成，不能派。不要绕过，也不要删依赖。
   - `already_assigned`：已经派过，跳过。
5. 分派只写负责人，不改状态。对方执行 `start` 后才变成进行中。

调度时机：建完子任务后、收到子任务完成的通知后、收到阻塞解除的通知后、每次被唤醒时。每次都从看板重新读取，不凭记忆。

bot 是否占用：该 bot 负责、状态为待分配（已派未开始）、进行中或阻塞的任务算占用。阻塞也算占用，不给它派新任务。正在协调子任务的父任务不算占用。

### 6. 巡检

被唤醒时看 `children` 里"进行中"子任务的修改时间。明显很久没更新的，在工作群里 @ 对应的 bot 询问进展。询问后仍无响应，或负责 bot 明显失联时，执行 `muxboard unassign <子任务ID> --note <原因>` 收回，再按「调度一轮」重新派发。

### 示例：做一个单文件 HTML 贪吃蛇，工作群里有 2 个 bot

规划出 5 个子任务：

1. 总体设计（高）：游戏状态的数据结构，逻辑、渲染、输入三个模块的函数签名，合成单个 `index.html` 的方式。无依赖。
2. 游戏逻辑（中）：移动、吃食物、增长、碰撞、计分，纯函数并自测。依赖 1。
3. 渲染与界面（中）：画布绘制、分数面板、暂停和结束遮罩、样式。依赖 1。
4. 输入与控制（中）：方向键和 WASD、反向拦截、暂停、重新开始、最高分持久化。依赖 1。
5. 集成与验收（中）：合成 `index.html`，按准出标准跑验收，修复问题。依赖 2、3、4。

调度过程：

- 第一轮：可派发的只有 1，派给 bot A。bot B 空闲但没有可派发任务，等待。
- 1 完成：可派发 2、3、4。派 2 给 A，3 给 B。4 排队。
- 2 完成：A 空闲，派 4 给 A。
- 3、4 完成：可派发 5，派给空闲的 bot。
- 5 完成：进入「收尾」。

## 执行中沟通

直接在工作群里回复对方，不需要执行命令。

## 任务被收回

收到「任务……已收回，请停止处理」的消息后，立即停止处理该任务，不再对它执行 `status`、`output` 等命令。已有的中间产出在群里简要说明即可。

## 受阻

缺少信息或依赖未完成、无法继续时，执行：

```
muxboard status <任务ID> 阻塞 --note <原因>
```

`--note` 必填，写清楚缺什么。阻塞期间你仍算占用，不会被派新任务，也不要自己去接别的任务。阻塞解除后执行 `muxboard status <任务ID> 进行中`，然后继续工作。

## 完成

1. 对照准出标准逐条自查。不满足就继续做，不要提前完成。
2. 执行 `muxboard output <任务ID> <产出>` 写入产出，比如 MR 链接、文档链接。
3. 执行 `muxboard status <任务ID> 已完成 --note <说明>`。

CLI 会在父任务的工作群里 @ 父任务的 bot 汇报；根任务则在根群里 @ 派发人。若你的任务还有未完成的子任务，CLI 会拒绝（`children_unfinished`），这时先等子任务完成。

完成后不要自己去找下一个任务，等派发方分派。

## 收到子任务的完成或受阻消息

1. 执行 `muxboard children <父任务ID>` 检查所有子任务状态。
2. 子任务完成：按「调度一轮」派下一个可派发任务。需要补充工作时，用 `add`（带 `--deps`、`--priority`）追加，再调度。
3. 子任务受阻：先看原因，自己尝试解决（补充信息、澄清约定、在工作群里回复）。解决不了就按需追加前置任务，或向上汇报。阻塞解除后再调度一轮。
4. 全部完成：进入「收尾」。

## 收尾

1. 子任务全部完成后，逐条对照父任务的准出标准核对，不能只看子任务是否都完成。
2. 需要集成或验收而规划里没有时，追加一个依赖全部子任务的集成任务并调度，不要直接把父任务标成完成。
3. 核对通过后执行 `muxboard status <父任务ID> 已完成 --note <说明>`，CLI 会继续往上汇报。

## 根任务

人在普通群里直接派发任务时，由收到派发的 bot 创建根任务。当前群就是根任务的群，子任务在这个群里分派。单聊、话题群里不能创建（`not_group_chat`）。

```
muxboard init --title <标题> --desc <描述> --criteria <准出标准> [--priority 高|中|低] --from <派发人 open_id>
```

- `--from` 填当前这条消息发送人的 open_id，不要填会话发起人。
- `--desc` 里可以写参考文档链接。
- `--priority` 不填时默认为"中"。
- 创建后得到任务 ID，后续命令都用它。CLI 会在群里发出看板链接，不需要再单独发。
- 还没有看板时，`init` 会自动新建一张；其他命令报 `board_not_initialized` 时，先用 `init` 创建根任务。

## 命令速查

| 命令 | 参数 | 用途 |
| --- | --- | --- |
| `init` | `--title <文本> --desc <文本> --criteria <文本> [--priority 高\|中\|低] [--from <open_id>]` | 在当前普通群创建根任务，负责人为自己，状态为进行中 |
| `show` | `<任务ID>` | 查看任务详情，含父任务、依赖和子任务计数 |
| `start` | `<任务ID>` | 开始处理，待分配改为进行中；其他状态不变，直接成功 |
| `children` | `<任务ID> [--status <状态>] [--ready]` | 列出直接子任务，含优先级、依赖、是否可派发（`ready`），按可派发 → 优先级 → 创建顺序排序；`--ready` 只列可派发的 |
| `add` | `<父任务ID> --title <文本> --desc <文本> --criteria <文本> [--priority 高\|中\|低] [--deps <ID,...>]` | 创建子任务，状态为待分配；依赖须为同一父任务下的子任务；父任务要先有工作群 |
| `split` | `<任务ID>` | 子任务要继续拆分时，为它新建工作群并拉入上级群的人和 bot |
| `assign` | `<子任务ID> --bot <app_id>` | 分派给 bot，写负责人、拉进工作群并 @ 它；状态不变。已派过、依赖未完成、bot 占用时拒绝 |
| `unassign` | `<子任务ID> [--note <原因>]` | 派发方收回已分派的子任务：清空负责人、改回待分配，并通知原负责 bot 停止处理 |
| `status` | `<任务ID> <进行中\|阻塞\|已完成> [--note <文本>]` | 更新状态并写当前进展；阻塞、已完成时必须带 `--note` |
| `output` | `<任务ID> <内容>` | 覆盖写入产出 |

状态只能是 `进行中`、`阻塞`、`已完成`。`待分配` 由 CLI 在建子任务时设置，不能手动设为待分配。

## 输出与错误

成功输出 `{"ok": true, "data": {...}}`，退出码为 0。

失败输出 `{"ok": false, "error": {"code": "...", "message": "..."}}`，退出码为 1。看 `error.code` 决定怎么处理：

| 错误码 | 含义 | 处理 |
| --- | --- | --- |
| `not_in_botmux` | 缺少 botmux 注入的环境变量 | 当前不在 botmux 会话中运行，不要重试，告知用户 |
| `not_found` | 任务 ID 不存在 | 核对 ID 是否写错（rec 开头），不要猜测 |
| `invalid_args` | 参数缺失或格式不对 | 按 `message` 修正参数后重试 |
| `invalid_status` | 状态值不合法 | 只用 `进行中`、`阻塞`、`已完成` |
| `note_required` | 设为阻塞或已完成时缺少 `--note` | 补上 `--note` 后重试 |
| `children_unfinished` | 还有未完成的子任务，不能设为已完成 | 先执行 `children` 查看并等待子任务完成 |
| `already_assigned` | 子任务已经派过（有负责人或不是待分配） | 跳过它，派下一个可派发任务；确需改派时，先 `muxboard unassign <子任务ID> --note <原因>` 收回，再重新 assign |
| `deps_unfinished` | 子任务的依赖还没全部完成 | 不能派，等依赖完成后再调度；不要删依赖绕过 |
| `bot_busy` | 目标 bot 手上已有占用中的任务 | 换一个空闲 bot；都忙时等待，在工作群里说明 |
| `not_dispatcher` | 不是父任务的负责人，不能 `unassign` | 只有派发方能收回；需要时告知父任务的 bot |
| `task_done` | 子任务已完成，不能 `unassign` | 不需要收回 |
| `not_assigned` | 子任务没有负责人 | 不需要收回，直接 `assign` |
| `not_group_chat` | 当前会话不是普通群，不能创建根任务 | 告知用户到普通群里派发任务 |
| `no_work_chat` | 找不到工作群 | `add` 时出现：先 `split <父任务ID>`；其他情况执行 `show` 查看父任务，必要时上报 |
| `bot_unresolved` | 群成员里找不到目标 bot，无法 @ | 稍后重试一次；仍失败则告知父任务的 bot |
| `lark_error` | lark-cli 调用失败，`message` 里有原始错误 | 原样记录错误信息；网络或权限问题可重试一次，仍失败则告知用户 |

## 约束

- 只用 `muxboard` 命令操作看板。不要直接调用 lark-cli 读写表格。
- 看板之外需要直接调用 lark-cli 时（如读文档、查群），用当前 bot 自己的身份：
  - 在 botmux 会话里直接用 PATH 上的 `lark-cli` 并加 `--as bot`，它已绑定当前 bot，不要再加 `--profile`，也不要改用 lark-cli 的真实安装路径。
  - 不经过 botmux 托管入口时，每次调用加 `--as bot --profile $BOTMUX_LARK_APP_ID`。
  - 不要用 `lark-cli profile use`、`config init`、`config bind`、`config default-as` 等方式切换全局默认身份，会影响同机其他 bot。
- 不要编造任务 ID。ID 只能来自 `init`、`add` 的输出，或收到的消息。
- 不要把任务设为已完成，除非准出标准已满足且子任务都已完成。
- 任务描述里可以写参考文档链接，但看板本身只存文字，不存附件。
